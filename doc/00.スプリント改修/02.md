# やりたいこと

SC-GAME の操作感と公正な対局開始を揃える。

1. **カード移動はドラッグ＆ドロップのみ**にする（タップでの選択→行先は廃止）。
2. **手を離したとき**、行先が不正または行先なしなら、カードが元の位置へ戻るアニメーションを付ける。
3. **9 と 10** の中央ピップ（スート記号）の位置ずれを直す。
4. **詰み判定**を実装し、利用者に提示する。
5. **新規配札は必ずクリア可能な山**にする。

修正実行の前に、このファイルの「確認事項」に合意する。未決のままコードを変えない。仕様と矛盾する変更は、先に `doc` を改訂してから実装する。

# 背景（現状の実装）

## 操作

対局 UI は `code/front/lib/game/presentation/game_page.dart`。フロント設計 5.3・画面一覧 3.4・BF-04 は **ドラッグとタップの両方** を必須にしている。

- 場札の表向き連なりは `Draggable` + 同時に `onTap`（`selectOrMove`）。
- 組札・捨て札・空列は `DragTarget` だが、**捨て札トップを掴む `Draggable` がない**。タップ選択が実質の移動手段になっている。
- 山札はタップで `DRAW` / `RECYCLE`。
- 不正ドロップ時、仕様は「元位置へ戻す（アニメーション可）」。実装は `childWhenDragging` の半透明残像と Flutter 既定のスナップのみで、**掴み位置へ戻る明示アニメーションはない**。

## 9 / 10 のピップ

`playing_card.dart` の `pipsFor`。座標は中央パディング内の正規化位置。9 は 2-2-1-2-2、10 は中央に 2 個足した配置。四隅インデックスと中央ピップが重なり、9・10 で記号がずれて見える。

## 詰み

規則エンジンは **1 手が合法か** だけ判定する。合法手の列挙、詰みフラグ、詰み UI はない。対局状態は `IN_PROGRESS` / `CLEARED` / `ABANDONED` のみ。

Klondike では山札が残ると `DRAW` / `RECYCLE` が合法のまま回り続ける。**合法手が 0 枚** と **クリア不能** は一致しない。

## 配札

`Deal.initialBoard` は `SecureRandom` の Fisher–Yates。解けない山の棄却も、解手順の保存もない。クライアントは配札を指定できない（この制約は維持する）。

# 正本・制約

- 操作: `doc/01.業務要件定義/業務要件定義.md` BF-04、受入条件 2（現状はタップ必須 → 本スプリントで改訂対象）
- 画面: `doc/02.システム要件定義/画面一覧.md` 3.4
- ジェスチャ: `doc/03.設計/フロント設計.md` 5.3（不正ドロップで戻す、は既にある）
- 配札: システム要件 2.3 / 5.2、規則エンジン設計 4（現状は一様乱数 → 改訂対象）
- カード見た目: フロント設計 5.4、スプリント 01（ピップ配置の修正のみ。カード部品の作り直しはしない）
- 市販デッキ画像は使わない。
- 正本はサーバ。クライアントが配札内容を指定する API は作らない。

# 確認事項（実装前に埋める）

## 1. カード移動のジェスチャ

[推奨] 場札・捨て札・組札からの **MOVE はドラッグ＆ドロップのみ**。タップの選択ハイライトと「2 回目で行先」は削除する。  
山札の Draw / Recycle は対象を掴む移動ではないので **タップのまま**。空の組札・空列はドロップ先のみ。

[ ] 山札もめくりをドラッグにする。  
[ ] タップ移動も残す（本ファイルのやりたいことと矛盾）。

合意: （ ◯ ）推奨を採用

## 2. 戻るアニメーション

[推奨] 次のとき、掴んだカード（連なりなら先頭＋重なり）が **掴み開始位置へ戻る** 明示アニメーション。API は送らない。

- ドロップ先がルール不正
- 盤面の外、または `DragTarget` 以外で手を離す

成功ドロップは現行どおり楽観更新。戻る時間は 200〜300ms 程度。山札タップにこのアニメーションは付けない。

[ ] Flutter `Draggable` の既定スナップのみで足りる。

合意: （ ◯ ）推奨を採用

## 3. 9 / 10 のピップ

[推奨] 一般的なトランプの 9（2 列×4 + 中央 1）と 10（2 列×4 + 中央上下 2）に合わせ、四隅インデックスと重ならないよう中央領域とピップ半径を調整する。2〜8・A・絵札は 01 の配置を壊さない。

合意: （ ◯ ）推奨を採用

## 4. 詰みの定義

完全な「数学的にクリア不能」は本スプリント対象外（探索コストと、山札循環のため）。

[推奨] **操作詰み**。次をすべて満たすとき詰みとする。対局 `status` は `IN_PROGRESS` のまま（クリアでも放棄でもない）。

- 合法な `MOVE` が 1 つもない（場札・捨て札・組札からの移動。組札→場札も含む）
- `DRAW` / `RECYCLE` を繰り返しても、捨て札トップを場札または組札に置ける状態にならない（山札＋捨て札を高々 1 周して判定）

提示: 対局画面上のダイアログ。アンドゥ（可なら）とやり直し。計測は止めない（中断扱いにしない）。

判定の正本はサーバ。`GameResponse` に詰みフラグを足す。クライアントは表示用に同じ規則で再計算してよいが、認定はサーバ。

[ ] クライアントだけの表示（API は変えない）。  
[ ] クリア不能の完全探索までやる。

合意: （ ◯ ）推奨を採用

## 5. 必ずクリアできる配札

「乱数で配って運任せ」をやめ、**サーバがクリア手順を 1 本見つけた山だけ**を新規対局にする。見つけられない山は捨てて配り直す。クライアントは配札も手順も指定できない。

[推奨] 乱数シャッフル → サーバ内ソルバがクリア手順を発見するまで棄却。手順は対局開始後にクライアントへ返さない（ヒント対象外）。`createGame` は制限時間内に成功すること。上限回数を超えたら 503 相当ではなく、最後に成功した生成を使うか回数を上げる（実装時に設計へ数値を書く）。

[ ] 完成形から逆再生して初期配置を作る（ソルバ不要、生成コストは別）。  
[ ] 既知のクリア済みシードを固定リストから引く。

合意: （ ◯ ）推奨を採用。上限は規則エンジン設計 4（24 回 × 12_000 ノード、その後 80_000）

# 完了条件

- 場札の連なり・捨て札トップ・組札トップをドラッグして合法な行先へドロップできる。タップでは MOVE できない。
- 山札タップで Draw / Recycle できる。
- 不正または行先なしで手を離すと、カードが元位置へ戻るアニメーションが見える。そのとき手数は増えない。
- 9・10 のピップが四隅インデックスと重ならず、2〜8 と並んでトランプの並びに見える。
- 操作詰みの盤面で、サーバ応答に詰みフラグがあり、対局画面がダイアログを出す。アンドゥ／やり直しができる。`status` は `IN_PROGRESS`。
- 新規対局・やり直しの初期盤は、サーバがクリア手順を確認済み。解けない一様乱数の山をそのまま出さない。
- 既存の合法判定・アンドゥ・保存再開・クリア認定は維持する。
- 改訂した `doc` と実装が一致する。
- iOS シミュレータ縦と、本番相当 Web（または `flutter run -d chrome`）で、ドラッグ成功／失敗戻り／山札タップ／9・10 の見た目を目視確認する。
