## 1. 設計方針

1. **正本はサーバ**。クライアントは写しと操作感（楽観更新・アニメーション）だけを持つ。
2. **規則は二重実装・同一仕様**。Java と Dart で同じ判定を置き、共通のテストベクタで揃える。共有バイナリは作らない。
3. **対局更新は利用者単位で直列**。`games.version` による楽観排他と、サーバ内の同一 `gameId` 直列化を併用する。
4. **秘密は環境変数**。JWT 鍵・DB 接続はリポジトリに置かない。
5. **本フェーズは最大 1 レプリカ**。セッションストアや分散ロックは導入しない。Container Apps のスケールゼロ（最小 0）を許容する。

## 2. 論理構成

```
code/front (Flutter)
  UI / ジェスチャ / 楽観更新 / トークン保管
           │  JSON / HTTP(S)
code/server (Spring Boot)
  認証・対局ユースケース・規則エンジン・永続化
           │  JDBC
SQL Server
  users / refresh_tokens / games / game_moves / game_results
```

| 境界 | 通過するもの | 通過しないもの |
| --- | --- | --- |
| アプリ → API | Bearer、操作意図（move / undo 等）、版数 | 経過時間の申告、配札内容、パスワード平文の再送（ログイン時以外） |
| API → DB | 正規化済みメール、パスワードハッシュ、盤面 JSON、操作履歴 | 生リフレッシュトークン、生パスワード |

## 4. 主要シーケンス

表記: C = クライアント、S = サーバ、DB = SQL Server。失敗系の HTTP は要件 8 章および API.md。

### 4.1 起動

```
C: セキュア領域から access / refresh を読む
  ├─ なし → SC-LOGIN
  └─ あり → GET /games/current
       ├─ 200 → SC-GAME（続けて POST …/resume）
       ├─ 404 → SC-HOME（GET /results/me?limit=1）
       └─ 401 → POST /auth/refresh
            ├─ 200 → current を再試行
            └─ 401 → トークン破棄 → SC-LOGIN
```

### 4.2 新規対局

```
C: POST /games { abandonExisting }
S: 利用者の IN_PROGRESS を検索（行ロック）
  ├─ あり かつ abandonExisting≠true → 409 GAME_IN_PROGRESS
  ├─ あり かつ true → 旧行 ABANDONED
  └─ なし / 放棄後 → 配札、games INSERT、201
C: SC-GAME。続けて resume（新規直後は timingStartedAt を配札時に now としてよい）
```

新規 INSERT 時は `timing_started_at = now`、`elapsed_ms = 0`、`version = 0`、`move_count = 0`。

### 4.3 手の適用（楽観更新）

```
C: 規則エンジンで合法か判定
  ├─ 不正 → 盤面を動かさない（API しない）
  └─ 合法 → UI を先に更新し、送信キューへ（同時に 1 本）
C: POST /games/{id}/moves { version, move }
S: 対局行ロック → version 照合
  ├─ 不一致 → 409 + 正本
  ├─ 不正 → 422 + 正本（DB 不変）
  └─ 合法 → board / move_count / elapsed / version 更新
            game_moves に APPLY 追加
            クリアなら CLEARED + game_results
            200 GameResponse
C: 200 → 応答で写しを置換（手数・時間・版を正本に合わせる）
   409 → 楽観を捨てて応答の盤面に置換
   422 → 楽観を捨てて正本に戻し短文
```

送信中に利用者が次の手をしても、**API は前の応答後にだけ送る**。画面の仮表示はしてよいが、キューは「未送信 1 手まで」とし、衝突したらサーバ応答後に再評価する（未送信の古い手は捨て、最新の正本に対する操作だけ残す）。

### 4.4 アンドゥ

```
C: POST …/undo { version }
S: 直近の未打消 APPLY を特定し、board / move_count を before に戻す
   elapsed_ms は戻さない。UNDO 行追加。version +1
```

### 4.5 中断・再開

```
対局画面入場: POST …/resume（計測開始。既に計測中なら二重加算しない）
ホームへ / バックグラウンド: POST …/pause
プロセスキル: pause が届かないことがある。
  次回 GET current は計測を変えない。入場 resume で再開。
  キル中の経過は業務上加算しない（フォアグラウンド累積）。
```

### 4.6 クリア

手の適用の結果として 4 組札が各 13 枚になったときのみ。同一トランザクションで `games` 更新と `game_results` INSERT。以降の moves / undo は 422。

## 5. 横断

### 5.1 認証ヘッダ

対局・ログアウト: `Authorization: Bearer <access_token>`。  
登録・ログイン・リフレッシュ: Bearer 不要。

### 5.2 時計

記録に使う時刻は **サーバ UTC** のみ。クライアントの `elapsedMs` 送信は API に存在させない。

### 5.3 ログ（サーバ）

残す: メソッド、パス、`userId`（取れるとき）、`gameId`、操作種別、HTTP ステータス、`code`。  
残さない: パスワード、Authorization、refresh 生値、盤面全文（障害調査が必要なら gameId + version まで）。

### 5.4 設定（論理名）

| 論理名 | 用途 |
| --- | --- |
| `DB_URL` / `DB_USER` / `DB_PASSWORD` | SQL Server |
| `JWT_ACCESS_SECRET` | アクセス JWT 署名 |
| `JWT_REFRESH_SECRET` | リフレッシュ JWT 署名（アクセスと分ける） |
| `CORS_ORIGINS` | 本フェーズはモバイル直叩き想定。不要なら空 |

開発は HTTP 可。本番相当は HTTPS 終端（リバースプロキシ可）。

### 5.5 開発起動順

1. SQL Server（データベース作成、マイグレーション適用）
2. `code/server`
3. `code/front`（API ベース URL を開発ホストへ）

対局〜保存〜再開がローカルで通ることを最初の結合条件とする。

### 5.6 本番配備

契約の正は `infra/azure-container-apps-契約.txt`。

```
[Flutter ネイティブ] -- HTTPS --> [Azure Container Apps Consumption] --> [Azure SQL]
[ブラウザ Flutter Web] -- 同一オリジン -->   Spring Boot（`/` UI + `/api/v1`）         正本
                                              最小レプリカ 0 / 最大 1
```

- イメージは GitHub Container Registry。ACR は使わない。JAR に `flutter build web` の静的ファイルを含める。
- デプロイスロットは使わない。入替は新リビジョン（新イメージ）の更新。
- 秘密は Container Apps のシークレット / 環境変数。リポジトリに置かない。
- HTTPS は環境のイングレス終端。ヘルスは `GET /api/v1/health`。UI は `GET /`。
- `/boot` `/login` `/register` `/home` `/game` は `index.html` へフォールバックする。
- スケールゼロ後の初回はコールドスタートする。クライアントは既存の 15 秒タイムアウト（SN-06）に従う。Web 初回表示は数十秒かかることがある。
